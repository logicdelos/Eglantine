# Eglantine system map

A map of the emulator's systems, written from the source at commit `0aae940355` (branch `fe-buf`, 3294 C/C++ files under `src/`), with the defects found while reading. Built for a Windows, Vulkan, NVIDIA target; Android and OpenGL paths were not studied.

## How to read it

- One page per system (`<slice>.md`): purpose, files, main types and who owns them, threads and locks, flow, connections, settings, invariants, hazards.
- `findings/<slice>.json`: every candidate defect or improvement from that page, with file, line and the quoted source line.
- `verify/<slice>.json`: a second, independent reading of every candidate rated medium or high, with a verdict: `confirmed`, `confirmed_narrow` (real, but only under conditions that are rare or off by default), `refuted`, or `unproven`.

Everything here comes from reading code unless the text says it was measured. Each quoted line was checked by script against the file. A verdict means a second reader could name the trigger from the code; it does not mean the fault was reproduced.

## Measured

Host: 15.6 GB RAM, 59.3 GB commit limit, RTX 5070 Ti Laptop (12 GB), Windows 11. Game: Fire Emblem: Fortune's Weave (`.nup`), `eden-cli`.

- **No unbounded growth in a 30 minute run.** Private memory levelled at 9281 to 9386 MB from 573 s on (one transient of 9521 MB), dedicated GPU memory stayed at 5682 to 5690 MB, handles about 3600, threads 130 to 133, and the log has no memory error. The run was stopped at 1780 s because free commit on the PC had fallen to 0.8 GB.
- **The emulator charged about 24 GB of commit**: 9.4 GB private plus the guest-RAM section, which was created fully committed (14,336 MiB) although about 1.5 GiB of it was resident. Stopping the emulator returned 24.1 GB of system commit. On a PC near its commit limit that is what makes allocations fail everywhere.
- **Guest RAM is now committed as it is used** (`HostMemory::Impl::Commit`, `EDEN_NX2_RAM_PRECOMMIT=1` restores the old behaviour). Measured 40 s into a run: 9,848 MiB committed of 14,336 in Fortune's Weave and in Xenoblade Chronicles 2, a saving of 4,488 MiB. The rest stays charged because the game maps 9.4 GiB in one `MapPhysicalMemory` call at boot and unmaps it again, and Windows cannot decommit pages of a section. Committing only on first touch would save more, but every place that hands a guest pointer to a Windows call (file and socket reads into guest memory) would have to be checked first; that check is not done.
- **`VK_EXT_vertex_input_dynamic_state` is disabled on this PC** by the faulty version test in `vulkan_device.cpp:1416`: the log prints `Disabling broken VK_EXT_vertex_input_dynamic_state` on the RTX 5070 Ti.
- **`Unmapped Device ReadBlock` errors: 16 in Fortune's Weave and 8 in Xenoblade Chronicles 2 per 96 s run before `f74d90d`, 0 in both after.** The cause is under [Fixes after the map](#fixes-after-the-map).
- **Unexplained: an 11.2 s pause before the game file loads, in four lab runs in a row**, then gone in the next two with the same `eden-cli.exe`. The log stops after the `Eden Version` line and resumes at the first `Loader` line. A sample taken during one pause shows the main thread in `NtReadFile` under `NupContainer::IsNupFile`, the first 4-byte read of the `.nup`, which is on a USB SSD. The same read from Python took 45 ms. No cause was found; if it returns, sample again with `EDEN_NX2_SAMPLE=* EDEN_NX2_SAMPLE_START=2`.

## Proposed order of work

The order puts confirmed faults with a simple, local fix first, then the items that could explain a freeze, then speed. Items 1 to 5 are fixed on branch `fe-buf`: 1 in `0bbc7a0`, 2 in `4ccb19f`, 3 in `a825773` and `c9d0f3a`, 4 in `1da6a28`, 5 in `b364934`. Items 6 to 8 are fixed except `nx2_gsv.h:144` and `npad.cpp:146`; each item names its commits, and [Fixes after the map](#fixes-after-the-map) says what was run and why those two are open. Of the fixes in 4 and 5, only the normal path was run (both games boot, render and play sound as before); the minimised window, a sound device that stops, a crash, an audio-out Stop then Start and a volume other than 100 % were not exercised.

1. **Vertex-input dynamic state is switched off on every NVIDIA and Intel Windows driver** (`vulkan_device.cpp:1416`). The version test compares a 29-bit masked `driverVersion` with constants built by `VK_MAKE_API_VERSION`, which are larger than any masked value, so it is always true. Measured: the log line `Disabling broken VK_EXT_vertex_input_dynamic_state` appears on the RTX 5070 Ti. The fix is to compare the raw `driverVersion` with each vendor's own packing (NVIDIA `major<<22 | minor<<14 | patch<<6`; Intel Windows `major<<14 | minor`). It changes which pipelines are built on this PC, so it needs a run of each game before and after.
2. **Writes that cross a 2 KiB boundary are not reported to the GPU caches** (`gpu_dirty_memory_manager.h:136`). The mask shift underflows, the upper chunk is never recorded, and the GPU keeps stale data. A candidate cause for textures or buffers that fail to update.
3. **Guest-chosen indexes and lengths used without a bounds check**: `cdma_pusher.cpp:108` and `nvdec.cpp:38` (register index), `nvhost_ctrl.cpp:104` (event id), `nifm.cpp:777` (SSID length, a stack overflow), `filesystem.cpp:207` (null source in a rename across directories), `key_manager.cpp:640`. Each is a one-line check. Normal games do not send these values; a damaged or hostile one could.
4. **Freeze candidates.** `vk_present_manager.cpp:580` (swapchain recreated in a loop while the window reports zero size, for example minimised; whether the NVIDIA driver returns the error that starts the loop is not settled by reading), `gpu.cpp:154` (a guest read-back waits with no way out at shutdown), `nvhost_ctrl.cpp:157` (unbounded wait while holding the events lock), `sink_stream.cpp:262` (audio thread blocks for good when the sound device stops consuming), `yuzu.cpp:565` (crash paths do not flush the log, so the last lines are lost). The stall watch added with this work writes every thread's call stack when no frame arrives for 60 s, so the next freeze names its own cause.
5. **Sound.** `device_session.cpp:134`: after a Stop then Start of an audio-out session no buffer is released again, and that session stays silent. `audio_controller.cpp:112`: volume is applied up to three times, so 50 % plays at about 14 % (0.53 × 0.53 × 0.5). The audio-out half of the first fix is in `src/audio_core/out/audio_out_system.cpp`, a directory that `.gitignore` (`out/`) keeps out of the repository: it is on disk and in the builds, not in a commit.
6. **Speed.** `texture_cache.h:214` (evicting an image the GPU modified stalls the GPU once per image, under memory pressure), `vk_pipeline_cache.cpp:2122` (a background pipeline build is thrown away when the draw then defers), `nup_container.cpp:212` (zstd members of a `.nup` are fully decompressed again on every cache miss), `vfs_real.cpp:370` (every read of a loose file takes one global lock), `system_manager.cpp:38` (audio manager thread spins when no renderer runs). Fixed: `texture_cache.h:214` in `2118911`, `vk_pipeline_cache.cpp:2122` in `6d94d18`, `nup_container.cpp:212` and `vfs_real.cpp:370` in `39216de`, `system_manager.cpp:38` in `fd1acac`. None was timed.
7. **Memory.** `nx2_gsv.h:144` (Switch 2 service sessions are never destroyed after the game closes them), `ncz_decompressor.cpp:361` (a solid NCZ install holds the whole decompressed file in memory), `host_memory.cpp:751` (the fallback allocation is not checked; with no commit left the emulator continues with a null base). Fixed: `ncz_decompressor.cpp:361` in `39216de`, `host_memory.cpp:751` in `970e98e`. Not fixed: `nx2_gsv.h:144`.
8. **Races with a small window** (fix when touching the code): `query_stream.h:114`, `bank_base.h:96`, `arm_dynarmic_64.cpp:545`, `npad.cpp:146`, `layer.cpp:223`, `texture_cache.h:2879`, `shader_cache.cpp:336`. Fixed: `query_stream.h:114`, `bank_base.h:96`, `layer.cpp:223` and `shader_cache.cpp:336` in `6d94d18`, `arm_dynarmic_64.cpp:545` in `970e98e`, `texture_cache.h:2879` in `700ab4e` and `2118911`. Not fixed: `npad.cpp:146`.

### Cause of the `Unmapped Device ReadBlock` errors

Every such line came from one caller: `RasterizerVulkan::Draw` → `BufferCache::BindHostStageBuffers` → `BindHostGraphicsUniformBuffer` → `SynchronizeBuffer` → `MappedUploadMemory` → `DeviceMemoryManager::ReadBlockUnsafe`.

When a shader indexes a uniform buffer with a computed offset, `collect_shader_info_pass.cpp:534` records the largest possible size, 0x10000 bytes. The binding seldom starts on a page boundary, so the range covers 17 pages, which is the `size = 69632` in the log. The first sync of a new `Buffer` uploads the whole range, but the game maps only the part it uses. In Fortune's Weave 2 of the 17 pages at `0x940e3000` are mapped; in Xenoblade Chronicles 2 the range at `0x131998000` has holes at pages 5 to 8 and 13 to 16.

The read already filled unmapped pages with zeros, so the uploaded bytes are the same before and after the fix. The error line was the only effect. Whether those draws render correctly was not checked.

The fix adds `DeviceMemoryManager::ReadBlockSparse`, which zero-fills unmapped pages and does not report. `SynchronizeBuffer` takes a `sparse_source` flag, and only `BindHostGraphicsUniformBuffer` sets it, when the binding size is exactly 0x10000. Every other unmapped read still reports.

One case is now silent that should not be: a shader that reads a constant offset in the last 16 bytes of the 64 KiB range also gets size 0x10000. Telling it apart needs a flag carried from the shader info to the binding. That was not added, because the data is zero-filled either way.

An unmapped device read now logs the host call stack, once per distinct start address and at most 16 times a run (`Nx2Sampler::CurrentStack`). That is how the caller was found, and it will name the caller of any new one.

### Not fixed

- **`nx2_gsv.h:144`, sessions never destroyed.** Moving the session handle to the client instead of copying it made Fortune's Weave abort at boot in `nn::gsv::BootWithRemoteMemory` (`SetTerminateResult` 0x2a2, error 2162-0001); the change was reverted. Two things must be solved before a session may be destroyed. `INx2GpuSession::SignalAfterGpu` and `QueueBackingRelease` hand the GPU thread a raw `this` and a raw `KEvent*`. The `Nx2SetSparseBacking` handler in `video_core/nx2.h:399` is one per process, and `~INx2GpuSession` clears it whichever session set it. A design that fits: a shared alive-state object as `INx2SyncptSession` has, or `shared_from_this()`, plus a clear that checks the owner.
- **`npad.cpp:146`, controller update without the lock.** `EmulatedController::TriggerOnChange` (`emulated_controller.cpp:1913`) holds `callback_mutex` and calls `NPad::ControllerUpdate` on an input or Qt thread, which touches the state that `OnUpdate` (`npad.cpp:491`) and `RequestPadStateUpdate` (`npad.cpp:422`) use on the CoreTiming thread under `shared_mutex`. Taking `shared_mutex` in `ControllerUpdate` deadlocks: `DisconnectNpad` holds `shared_mutex` and calls `device->Disconnect()`, which takes `callback_mutex`. Three other designs were tried and review found a fault in each: one lost a reconnect, one reset the dual Joy-Con flag, and one relied on a thread-local guard to suppress the re-entry. The files are back at `473b1df`. A design that fits: `TriggerOnChange` copies the callback list, releases `callback_mutex`, then calls; `ControllerUpdate` can then take `shared_mutex`. The race has not been seen in a run.

### Found along the way

- **dbghelp initialises once per process.** Each `Symbolizer` in `common/nx2_sampler.cpp` called `SymInitialize`. The second call fails, so every stack report after the first one in a run had addresses and no function names. Since `f74d90d` a failure with `ERROR_INVALID_PARAMETER` counts as already initialised, and one mutex (`symbol_mutex`) covers all dbghelp calls, which are not thread-safe.
- **Nothing assigns `m_active_target`** in `audio_controller.cpp`; it stays `Speaker`. Since `fd1acac` only a mute of the speaker target mutes the output.
- **The audio manager thread still spins in two cases**, found by reading, not measured: an active renderer on the null sink, and audio session 1 active while session 0 is closed.
- **`InstallNCA` in `content_manager.h` ignores a short read or write**, as `InstallNSP` did. It and `VfsRawCopy` (`registered_cache.cpp:464`) are unchanged.
- **`ShaderCache::RemovePendingShaders` frees `ShaderInfo` objects without setting `Dirty::Shaders`.** Any code that keeps a `ShaderInfo*` across a tick must compare `invalidation_serial`, as `RefreshStages` now does.
- **An image the garbage collector evicts must stay tracked and registered until its download is written to guest memory.** A guest write in between then still faults and waits for the cache. `2118911` keeps that order; a change that untracks first would let the write-back overwrite newer guest data.
- **A killed emulator loses the end of its log.** The lab stops `eden-cli` with `taskkill`; the last lines are unflushed and the file can end mid-line. Counts of periodic lines such as `diag 1s` differ by a few between runs for that reason alone.
